## 1. 项目背景与目标

### 1.1 背景与问题陈述

当前 AI 辅助开发工具（Cursor、v0、Bolt.new、墨刀 AI 等）各自解决单一环节：原型工具解决"画界面"，代码助手解决"写代码"，但二者之间存在三处断裂：

1. **原型与代码断裂**：设计稿是图片，代码是文本，二者无结构化映射关系，设计修改无法增量回灌到代码。
2. **上下文断裂**：AI 每次调用都是"失忆"的，用户的长期偏好、项目约定、页面结构、历史踩坑无法被稳定复用，导致反复纠正。
3. **管控断裂**：生成过程不透明、不可回退、不可定点修改，用户只能"整体重生成"，难以在工程上收敛。

EveryoneCoding 的目标是：以**分层记忆系统**为核心，以**可视化设计器**为交互入口，以**状态机化的开发流水线**为流程骨架，把"需求 → 界面 → 技术文档 → 代码"这条链路变成可观测、可回退、可增量修改的工程化过程。

### 1.2 产品定位

> 面向个人开发者与小型团队的 **Windows 桌面端 AI 全栈开发工作台**：  
> 用拖拽定义界面，用分层记忆沉淀知识，用流水线驱动 AI 逐步生成前端与后端代码，全程可视化、可回退、可定点修改。

### 1.3 目标用户

| 用户画像            | 特征            | 核心诉求           | 关键场景                     |
| --------------- | ------------- | -------------- | ------------------------ |
| 独立开发者 / 全栈工程师   | 1 人负责全链路，追求效率 | 从想法到可运行项目的时间最短 | 拖拽搭界面 → 生成技术文档 → 分功能生成代码 |
| 产品经理 / 设计师（懂技术） | 会画原型，代码能力弱    | 原型直接变成可运行代码    | 墨刀式拖拽 → AI 生成前后端         |
| 中小团队技术负责人       | 需要统一规范        | 团队偏好与架构约定被稳定遵守 | 导出记忆包分发 + 用户自配远程配置源      |
| 编程学习者           | 需要理解生成逻辑      | 看得懂每一步为什么      | 逻辑结构可视化 + Ctrl 跳转后端      |

### 1.4 核心价值主张

1. **记忆驱动**：分层记忆（长期 / 项目 / 功能 / 页面 / 问题）让 AI 越用越懂你，减少重复纠正。
2. **结构化界面**：拖拽产生的不是图片，而是可被 AI 与代码双向消费的 **结构化页面 DSL**。
3. **流程可控**：7 阶段流水线，每阶段产物可见、可编辑、可回退，拒绝"一键黑盒"。
4. **定点修改**：项目完成后，可精确到"某个页面的某个元素"重新生成，而非整体重来。
5. **全程可视化**：设计、记忆、Git、AI 调用、后端映射，全部图形化，无命令行依赖。

### 1.5 成功指标（建议）

| 指标     | 定义                        | 目标值（MVP 后 3 个月） |
| ------ | ------------------------- | --------------- |
| 端到端完成率 | 完成 7 阶段并产出可运行项目的比例        | ≥ 60%           |
| 重复纠正下降 | 同一偏好被用户重复纠正次数             | 较基线下降 ≥ 50%     |
| 定点修改占比 | 使用元素级 / 页面级重生成的次数占总生成次数比例 | ≥ 40%           |
| 日活留存   | 注册用户 7 日留存                | ≥ 35%           |
| 首项目时长  | 注册到产出第一个可运行项目的中位时长        | ≤ 90 分钟         |

## 2. 术语与概念模型

| 术语   | 英文 / 缩写                | 定义                                                      |
| ---- | ---------------------- | ------------------------------------------------------- |
| 工作区  | Workspace              | 客户端本地管理的根容器，包含多个项目与全局记忆库                                |
| 项目   | Project                | 一个完整应用（前端 + 后端），是流程与记忆的主维度                              |
| 功能   | Feature                | 项目内的一级业务能力单元（如"用户登录""订单支付"），可跨页面                        |
| 页面   | Page                   | 前端可路由的界面单元，属于某个目标端（Web / Android / iOS / HarmonyOS / Windows / Linux / macOS 七端之一） |
| 元素   | Element                | 页面内的最小可操作节点（按钮、表单、列表、容器……），可嵌套                          |
| 逻辑结构 | Logic Structure        | 由设计器 DSL 精简而来的结构化摘要（组件树 / 状态 / 事件 / 数据流 / 接口依赖），分层存储于记忆 |
| 长期记忆 | Long-term Memory (LTM) | 跨项目生效的用户级知识：技术偏好、编码规范、UI 风格、禁止事项                        |
| 项目记忆 | Project Memory (PM)    | 项目级知识：技术选型、模块划分、数据模型、全局约定                               |
| 功能记忆 | Feature Memory (FM)    | 功能级知识：业务流程、输入输出、边界条件、接口清单、错误码                           |
| 页面记忆 | Page Memory (PaM)      | 页面级知识：布局骨架、区块结构、状态机、事件流                                 |
| 问题记忆 | Issue Memory (IM)      | 针对某个具体缺陷/难题的专项记忆：现象、复现、尝试过的方案、结论                        |
| 元素备注 | Element Note           | 挂在单个元素上的批注（业务规则、校验要求、交互说明）                              |
| 流水线  | Pipeline               | 7 阶段开发流程的状态机（需求 → 界面 → 技术文档 → 生成 → 完成）                  |
| 代码锚点 | Code Anchor            | 元素/页面/功能 与 后端代码位置（控制器、Service、SQL、测试）的映射关系              |
| 中转   | Provider / Gateway     | 兼容 OpenAI 或 Anthropic 协议的第三方 API 服务                     |
| 远程配置 | Remote Config          | 由服务端下发的默认 Provider 与默认模型配置                              |

### 2.1 记忆分层关系

```
长期记忆 (LTM)  ── 跨项目，全局生效
      │
      ▼
项目记忆 (PM)   ── 单项目：架构 / 技术栈 / 数据模型 / 全局约定
      │
      ├── 功能记忆 (FM) ── 业务流程 / 接口 / 错误码
      │        │
      │        └── 问题记忆 (IM) ── 挂在功能或页面下的具体缺陷
      │
      └── 页面记忆 (PaM) ── 布局 / 区块 / 状态 / 事件
               │
               └── 元素备注 (Note) ── 挂在具体节点上的批注
```

**继承与覆盖规则**：下层记忆在 AI 上下文中自动携带其所有上层记忆；同名/同键冲突时，**下层覆盖上层**（就近优先），并在 UI 中标注冲突来源。

### 2.2 已确认决策与硬约束

以下决策已经产品方确认，需求细节必须与其保持一致。

| 编号 | 决策项 | 结论 |
| --- | --- | --- |
| D-01 | 客户端外壳 | **Tauri 2 与 Electron 双形态并存**，由用户选择下载哪个版本；功能层通过外壳抽象隔离，两版功能等价 |
| D-02 | 记忆同步 | **只做本地存储 + 手动导出/导入**（`.ecpkg`），不做云端自动同步 |
| D-03 | 目标端与多端产物 | **必须真实生成七端中所选目标端的可运行代码**（Web / Android / iOS / HarmonyOS / Windows / Linux / macOS）；各端方案在技术文档阶段由用户确认，默认推荐：Web 用 React，Android / iOS 用 Flutter（单代码库覆盖双端），HarmonyOS 用 ArkTS + ArkUI，桌面三端（Windows / Linux / macOS）用 Tauri 2（与客户端外壳同栈，可单代码库覆盖三端） |
| D-04 | 技术栈与代码写入 | 技术选型在**技术文档阶段询问用户**后确定；**代码与数据库脚本一律不允许用户手动修改，只能由 AI 生成或修改** |
| D-05 | 团队协作 | **v1.x 不支持**多人共享项目与记忆 |
| D-06 | 远程配置 | **不提供平台运营的远程配置服务**；改为客户端内独立的「远程配置页面」，由用户自行填写与维护 |
| D-07 | 重命名范围 | **仅项目内生效，不跨项目联动**，也不自动修改长期记忆与其他项目中的引用 |
| D-08 | 数据库改名 | DDL 由 AI 生成迁移脚本，**用户确认后可一键执行迁移**；数据库相关代码同样只能由 AI 生成/修改 |
| D-09 | `.ecpkg` 分发 | **不对接对象存储、不生成云端分享链接**，仅本地文件 |
| D-10 | 中文命名 | **组件名与标识符用英文/拼音，显示文案保留中文** |

**贯穿全文档的硬约束**

1. **AI 是代码与数据库脚本的唯一写入口**：客户端内代码视图为只读，用户不可手动编辑；一切修改通过 AI 生成完成（FR-AI-11）。
2. **数据本地优先**：项目、记忆、文档全部存放本地；云端仅承担账号注册/登录（D-02、D-06）。
3. **不跨项目自动联动**（D-07）：跨项目复用通过 `.ecpkg` 文件手动导入完成。

### 3.2 技术选型（D-01 / D-03 / D-04 已确认）

| 层       | 选定方案                                                             | 备选 / 说明                                                                    |
| ------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 客户端外壳   | **Tauri 2 与 Electron 双形态并存，用户下载时自选**（D-01）                        | 两版功能等价；外壳能力（文件、进程、窗口、密钥环、更新）抽象为统一接口，业务逻辑零感知。Tauri 版包体小、内存低；Electron 版生态成熟、人力成本低 |
| 前端框架    | React 18 + TypeScript                                            | 同时作为 Electron 渲染层与 Tauri WebView 层                                        |
| 画布渲染    | **DOM + CSS Transform**（所见即所得）                                   | DOM 渲染与最终 Web 产物一致，样式零失真                                                   |
| 状态管理    | Zustand + Immer + Zundo（撤销/重做）                                   | 设计器文档树需要 patch 级 undo                                                      |
| 拖拽引擎    | dnd-kit（碰撞检测、吸附、参考线）                                             | 支持嵌套容器与自由布局两种模式                                                            |
| 本地存储    | SQLite（FTS5 + sqlite-vec 向量扩展）                                   | **仅本地**（D-02），无云端同步                                                        |
| Git     | **git2 (libgit2)** 优先，回退系统 git CLI                               | 变更来源为 AI 生成节点与迁移执行，用户不手改代码（D-04）                                           |
| AI 适配   | 自研 Provider Adapter（OpenAI / Anthropic 双协议）                       | 需精细控制上下文裁剪与协议差异                                                            |
| 预览服务    | 内置 Mock Server + 子进程运行真实后端                                       | 满足"动态关联后台逻辑"诉求                                                             |
| 多端产物生成 | **七端技术方案矩阵（D-03）**：Web → React 18（默认）/ Vue 3；Android / iOS → Flutter（默认，单代码库覆盖双端）/ React Native / 原生双端；HarmonyOS → ArkTS + ArkUI（Stage 模型，v1.0 唯一推荐方案）；Windows / Linux / macOS → Tauri 2（默认，单代码库覆盖桌面三端）/ Electron / Qt（P2） | 因代码不可手改（D-04），同组端优先单代码库方案以降低端间不一致风险；移动端与桌面端可共用后端契约；鸿蒙端独立维护 ArkTS 工程 |
| 后端技术栈   | **技术文档阶段由用户确认**（D-04），推荐 NestJS 或 FastAPI 模板起步                   | 一旦确定即写入项目记忆并全程遵守                                                           |
| 打包分发    | Tauri 版用 Tauri Updater；Electron 版用 electron-updater；均出 NSIS 安装包  | 双形态共用同一版本号与更新通道                                                            |

### 3.3 客户端进程结构

| 进程 / 模块                     | 职责                                                     |
| --------------------------- | ------------------------------------------------------ |
| Core（Tauri 版：Rust；Electron 版：Node 主进程） | 文件系统、Git、进程管理、SQLite、密钥存储（DPAPI）、自动更新；向上暴露统一外壳接口 |
| Renderer                    | 设计器、记忆中心、AI 工作台、Git 面板、设置；**代码视图为只读**（D-04）            |
| Preview Server              | 本地预览：静态资源服务 + Mock Server + 真实后端进程托管                   |
| AI Gateway Client           | 统一出口：协议适配、流式、重试、Token 计费统计                             |

### 3.4 关键数据流

1. **设计 → 记忆**：设计器 DSL → 结构精简器（Structure Condenser）→ 分层写入 页面/项目/功能 记忆。
2. **记忆 → AI**：上下文引擎（Context Engine）按预算与优先级组装 记忆 + 备注 + 需求 + 技术文档 → 提交模型。
3. **AI → 代码**：生成代码 → 写入工程（**唯一写入口**）→ 记录 Code Anchor → Git 自动提交（可配置）→ 预览服务热更新。
4. **交互 → 记忆**：用户纠正 / 反复 debug / 文档关联 → 自动写入或提示写入对应层级记忆。

**页面 DSL 核心结构（示意）**

```ts
interface PageDSL {
  id: string;
  projectId: string;
  name: string;
  platform: 'web' | 'android' | 'ios' | 'harmonyos' | 'windows' | 'linux' | 'macos';
  route: string;                    // '/user/profile'
  viewport: { width: number; height: number };
  state: Array<{ name: string; type: string; initial?: unknown; source?: 'local' | 'api' }>;
  tree: ElementNode;                // 组件树（递归）
  events: Array<{ id, trigger, actions: Action[] }>;
  apiDeps: string[];                // 依赖的接口 id
  notes: Note[];                    // 元素/页面备注
  anchors: Record<string, CodeAnchor>; // 元素 → 后端代码位置映射
}

interface ElementNode {
  id: string;
  type: string;                     // 'Button' | 'Form' | ...
  props: Record<string, unknown>;
  style: Record<string, unknown>;
  bindings?: Record<string, string>;// 属性 → 状态/接口字段
  children?: ElementNode[];
  noteId?: string;
}
```

### M7 开发流水线（`FR-PIPE`）—— 对应需求 13

流水线是整个产品的流程骨架，采用**显式状态机**，每个阶段产出可见、可编辑、可回退的产物。

#### 7.1 阶段定义

| 阶段 | 名称      | 输入               | 产出物                                      | 完成条件            |
| -- | ------- | ---------------- | ---------------------------------------- | --------------- |
| S1 | 需求文档生成  | 用户自然语言描述         | `需求文档 v1`（功能列表、用户故事、验收标准、非功能要求）          | 用户点击"满意并进入下一阶段" |
| S2 | 界面设计    | 需求文档             | 页面 DSL（拖拽或 AI 生成）                        | 用户确认设计稿         |
| S3 | 技术文档生成  | 需求文档 + 页面结构 + 记忆 | `技术文档 v1`（技术选型、软件架构、模块划分、数据模型、接口设计、部署方案） | 用户确认技术文档        |
| S4 | 功能与页面拆分 | 技术文档             | 功能树 + 页面清单 + 依赖拓扑                        | 用户确认拆分结果        |
| S5 | 逐个生成    | 拆分结果 + 全部记忆      | 按拓扑序逐个生成功能与页面代码                          | 全部节点生成完成        |
| S6 | 集成联调    | 生成的代码            | 可运行项目 + 预览环境                             | 项目启动成功且冒烟用例通过   |
| S7 | 交付与维护   | 可运行项目            | Git 仓库 + 部署配置                            | 用户确认交付          |

> 注：需求 13 描述的顺序为 需求文档 → 界面 → 技术文档 → 逐个生成。上表 S1–S7 为其工程化展开，其中 S4（拆分）与 S6/S7（联调交付）为强化环节，可在 MVP 中以简化形态提供。

### M15 全局统一模块（`FR-UNI`）—— 新增需求 20

在交互式页面上修改一个元素的名称后，**自动同步修改**前端代码、后端代码、所有提及它的文档、记忆与逻辑结构。该模块是命名一致性的唯一事实来源。

#### 15.1 核心机制

**统一标识注册表（Canonical Symbol Registry）**

每个可命名对象（元素 / 页面 / 功能）持有：

- **稳定 ID**：不可变，所有引用关系的真正锚点（ULID）
- **规范名（Canonical Name）**：用户可见、可修改的名称
- **标识符投影（Projections）**：由规范名按命名规则派生的一组符号

| 投影类型      | 示例（规范名：用户登录按钮）                     | 目标位置                 |
| --------- | ---------------------------------- | -------------------- |
| 组件名       | `UserLoginButton`                  | 前端组件文件与引用            |
| 变量名 / 状态键 | `userLoginButton`                  | 前端状态、事件动作流           |
| CSS 类名    | `user-login-button`                | 样式定义与选择器             |
| i18n Key  | `page.login.userLoginButton.label` | 语言包                  |
| API 字段名   | `user_login_button`                | 请求/响应体、DTO           |
| 后端方法名     | `handleUserLoginButton`            | Controller / Service |
| 路由片段      | `/user-login-button`               | 路由表（仅页面 / 功能级）       |
| 测试用例名     | `should render UserLoginButton`    | 单测文件                 |

**出现位置索引（Occurrence Index）**：注册表同时记录每个投影在 **代码 / 文档 / 记忆 / 逻辑结构** 中的位置（文件 + 行列 / 文档段落 / 记忆条目），构成重命名的影响面。

#### 15.2 重命名流程

```
用户在设计器修改元素名称
        │
        ▼
① 合法性校验（保留字 / 冲突 / 非法字符 / 长度）── 不通过则阻断并给出建议名
        │
        ▼
② 生成新投影（按命名规则模板）
        │
        ▼
③ 影响面分析（Occurrence Index + AST 引用图）
   ├─ 自动区（安全，直接改）：组件名、变量名、CSS 类、i18n key、逻辑结构
   ├─ 确认区（需用户勾选）：API 字段名、DTO 字段、Service 方法
   └─ 警告区（默认不改）：数据库列名、已发布外部 API 路径、跨项目引用
        │
        ▼
④ 统一 diff 预览（代码 / 文档 / 记忆 / 逻辑结构 四栏）
        │
        ▼
⑤ 事务化执行：AST 级重构 → 文档替换 → 记忆更新 → 逻辑结构重算 → 注册表与锚点更新
        │
        ▼
⑥ 记录 rename 事件 + Git 提交（refactor(rename): A → B）→ 支持一键撤销
```

#### 15.3 需求清单

| 编号        | 需求描述                                                                                                 | 验收要点                                  | 优先级 |
| --------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------- | --- |

```

  │              │

  │              ├──1:N── Document

MemoryItem ──N:M── Document (MemoryDocLink)
```

### 9.2 元素选中 → 生成后端代码（需求 12）时序

1. 用户在画布选中元素 E（或图层树中选中）。
2. 上下文引擎收集：E 的祖先链结构、E 的备注、页面记忆、E 所属功能记忆、项目记忆、长期记忆、关联问题记忆、关联文档片段、Code Anchor 命中的已有代码。
3. 按 Token 预算裁剪 → 在"上下文面板"可视化展示，用户可勾选/编辑/补充指令。
4. 提交模型（流式）→ 返回结构化结果（文件列表 + 内容 + Anchor 声明）。
5. 展示 diff → 用户选择应用/部分应用/放弃。
6. 应用后写回 Code Anchor，更新 Git 变更视图，触发预览热更新。
7. 生成"AI 决策说明"卡片（引用了哪些记忆/备注）。

### 9.3 反复 Debug → 问题记忆（需求 7）时序

1. 检测器维护滚动窗口事件队列（生成/运行/报错/用户否定反馈）。
2. 命中阈值（10 分钟内 ≥3 次循环 或 同一错误 ≥2 次）。
3. 非模态提示卡出现 → 用户选择"立即建立"。
4. 自动汇总：错误信息、尝试过的方案（来自对话）、相关代码片段与 commit、关联元素/页面/功能。
5. 生成问题记忆草稿 → 用户补充 → 保存。
6. 该记忆此后自动进入相关上下文，并在记忆中心高亮显示。

### 13.2 AI 提示词组装策略要点

1. **角色与输出契约前置**：系统提示中明确输出 JSON Schema、Code Anchor 回写格式、禁止臆造接口。
2. **记忆按层排序**：长期 → 项目 → 功能 → 页面 → 元素，越靠后越具体、优先级越高。
3. **禁止事项用强约束句式**：`"以下为硬性约束，任何情况下不得违反：<长期记忆中的禁止项>"`。
4. **状态一致性**：注入"已生成依赖的接口契约"而非全部代码，避免上下文膨胀与前后矛盾。
5. **可控性要求**：要求模型输出"变更说明 + 风险 + 未覆盖点"，便于人工审核。
6. **失败兜底**：结构化解析失败时，降级为正则提取代码块；仍失败则原样展示并提示用户手动处理。

### 13.3 AI 调用错误码与处理

| 错误类型           | 客户端处理                                   |
| -------------- | --------------------------------------- |
| 401 / 403 鉴权失败 | 提示"API Key 无效或已过期"，引导至 Provider 设置页重新测试 |
| 402 余额不足       | 提示充值或切换备用 Provider                      |
| 408 / 超时       | 指数退避重试 ≤ 3 次；仍失败提示缩短上下文或换模型             |
| 429 限流         | 按 `Retry-After` 排队；展示排队位次               |
| 5xx            | 重试 ≤ 3 次；可选切换备用 Provider                |
| 内容过滤           | 明确提示"模型拒绝了该请求"并展示原因，建议改写指令              |
| 上下文超限          | 自动触发更激进裁剪（保留元素链 + 备注 + 页面记忆）并重试一次       |
| 协议不兼容          | 提示"该中转不兼容所选协议格式"，建议切换协议类型并展示实际返回片段      |
