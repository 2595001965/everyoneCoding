# EveryoneCoding

> 面向个人开发者与小型团队的 **Windows 桌面端 AI 全栈开发工作台**：用拖拽定义界面，用分层记忆沉淀知识，用流水线驱动 AI 逐步生成前端与后端代码，全程可视化、可回退、可定点修改。
>
> **多端产物支持**：一套「需求 → 界面 → 技术文档 → 代码」链路，可产出运行于 **Web（原生网页）、Android、iOS、HarmonyOS（鸿蒙）、Windows、Linux、macOS** 七端的原生应用。

| 项目     | 内容                                                                |
| ------ | ----------------------------------------------------------------- |
| 产品形态   | Windows 桌面客户端（本地安装，非纯 Web）                                        |
| 目标平台   | Windows 10 1809 (Build 17763)+ / Windows 11，x64（ARM64 为 P2 规划）    |
| 需求基线   | [PRD v1.3](docs/PRD-EveryoneCoding.md)（15 个模块 / 162 条功能需求） |
| 当前状态   | **Wave 0 工程底座已完成**：双形态外壳空壳可启动、SQLite 迁移可执行、UI 组件库可用、崩溃可恢复；功能开发按 `docs/tasks/` 的 Wave 1–10 推进          |

## 一、它解决什么问题

当前 AI 辅助开发工具（Cursor、v0、Bolt.new、墨刀 AI 等）各自只解决单一环节，链路中存在三处断裂：

1. **原型与代码断裂** — 设计稿是图片，代码是文本，二者无结构化映射，设计修改无法增量回灌到代码。
2. **上下文断裂** — AI 每次调用都是"失忆"的，长期偏好、项目约定、页面结构、历史踩坑无法被稳定复用，导致反复纠正。
3. **管控断裂** — 生成过程不透明、不可回退、不可定点修改，用户只能"整体重生成"，难以在工程上收敛。

EveryoneCoding 的思路是：以**分层记忆系统**为核心，以**可视化设计器**为交互入口，以**状态机化的开发流水线**为流程骨架，把「需求 → 界面 → 技术文档 → 代码」变成一条可观测、可回退、可增量修改的工程化链路。

### 目标用户

| 用户画像            | 核心诉求           | 关键场景                     |
| --------------- | -------------- | ------------------------ |
| 独立开发者 / 全栈工程师   | 从想法到可运行项目的时间最短 | 拖拽搭界面 → 生成技术文档 → 分功能生成代码 |
| 产品经理 / 设计师（懂技术） | 原型直接变成可运行代码    | 墨刀式拖拽 → AI 生成前后端         |
| 中小团队技术负责人       | 团队偏好与架构约定被稳定遵守 | 导出记忆包分发 + 用户自配远程配置源      |
| 编程学习者           | 看得懂每一步为什么      | 逻辑结构可视化 + Ctrl 跳转后端代码    |

## 二、核心特性

| # | 特性             | 说明                                                                                 |
| - | -------------- | ---------------------------------------------------------------------------------- |
| 1 | **记忆驱动**       | 五层记忆（长期 / 项目 / 功能 / 页面 / 问题）自动沉淀，下层自动继承上层、冲突时就近覆盖，让 AI 越用越懂你，减少重复纠正   |
| 2 | **结构化界面**      | 拖拽产出的不是图片，而是可被 AI 与代码双向消费的**结构化页面 DSL**；支持 Web / Android / iOS / HarmonyOS / Windows / Linux / macOS 七端目标 |
| 3 | **流程可控**       | 7 阶段流水线（S1–S7）显式状态机，每阶段产物版本化、可编辑、可回退，拒绝"一键黑盒"                                     |
| 4 | **定点修改**       | 项目完成后可精确到「某个页面的某个元素」重新生成，而非整体重来                                                    |
| 5 | **全程可视化**      | 设计、记忆、Git、AI 调用、后端映射（代码锚点）全部图形化，无命令行依赖                                             |
| 6 | **命名一致性引擎**    | 改一个元素名 → 前后端代码、文档、记忆、逻辑结构级联同步；影响面分析 + 三级风险分级 + 事务化回滚                             |
| 7 | **工程可迁移**      | `.ecpkg` 自定义归档格式，打包全部记忆、文档与项目代码，支持加密、脱敏与增量                                       |

### 记忆分层模型

```
长期记忆 (LTM)  ── 跨项目，全局生效：技术偏好 / 编码规范 / UI 风格 / 禁止事项
      │
      ▼
项目记忆 (PM)   ── 单项目：技术栈 / 模块划分 / 数据模型 / 全局约定
      │
      ├── 功能记忆 (FM) ── 业务流程 / 接口 / 错误码
      │        │
      │        └── 问题记忆 (IM) ── 挂在功能或页面下的具体缺陷（现象 / 复现 / 尝试 / 结论）
      │
      └── 页面记忆 (PaM) ── 布局 / 区块 / 状态机 / 事件流
               │
               └── 元素备注 (Note) ── 挂在具体节点上的批注
```

继承与覆盖规则：下层记忆在 AI 上下文中自动携带其所有上层记忆；同名 / 同键冲突时**下层覆盖上层**（就近优先），并在 UI 中标注冲突来源。

### 开发流水线（7 阶段）

| 阶段 | 名称      | 输入                | 产出物                          |
| -- | ------- | ----------------- | ---------------------------- |
| S1 | 需求文档生成  | 用户自然语言描述          | 需求文档 v1（功能清单、用户故事、验收标准、非功能要求） |
| S2 | 界面设计    | 需求文档              | 页面 DSL（拖拽或 AI 生成）            |
| S3 | 技术文档生成  | 需求文档 + 页面结构 + 记忆  | 技术文档 v1（选型、架构、数据模型、接口设计、部署方案） |
| S4 | 功能与页面拆分 | 技术文档              | 功能树 + 页面清单 + 依赖拓扑（DAG）        |
| S5 | 逐个生成    | 拆分结果 + 全部记忆       | 按拓扑序逐个生成功能与页面代码               |
| S6 | 集成联调    | 生成的代码             | 可运行项目 + 预览环境                 |
| S7 | 交付与维护   | 可运行项目             | Git 仓库 + 部署配置                |

每阶段均提供「重新生成 / 局部修改 / 手动编辑 / 追加要求」四种操作，构成"修改至满意"闭环。

## 三、技术选型

| 层        | 选定方案                                                                  | 说明                                            |
| -------- | --------------------------------------------------------------------- | --------------------------------------------- |
| 客户端外壳    | **Tauri 2 与 Electron 双形态并存**，用户下载时自选                                   | 两版功能等价；外壳能力（文件、进程、窗口、密钥环、更新）抽象为统一接口，业务逻辑零感知 |
| 前端框架     | React 18 + TypeScript                                                 | 同时作为 Electron 渲染层与 Tauri WebView 层           |
| 画布渲染     | DOM + CSS Transform（所见即所得）                                            | DOM 渲染与最终 Web 产物一致，样式零失真                      |
| 状态管理     | Zustand + Immer + Zundo（撤销 / 重做）                                      | 设计器文档树需要 patch 级 undo                         |
| 拖拽引擎     | dnd-kit（碰撞检测、吸附、参考线）                                                  | 支持嵌套容器与自由布局两种模式                               |
| 本地存储     | SQLite（FTS5 + sqlite-vec 向量扩展）                                        | **仅本地**，无云端同步                                 |
| Git      | git2 (libgit2) 优先，回退系统 git CLI                                        | 变更来源为 AI 生成节点、重命名事务与迁移执行                      |
| AI 适配    | 自研 Provider Adapter（OpenAI / Anthropic 双协议）                           | 需精细控制上下文裁剪与协议差异                               |
| 预览服务     | 内置 Mock Server + 子进程运行真实后端                                            | 满足"动态关联后台逻辑"诉求                                |
| 多端产物生成  | **七端技术方案矩阵**：Web → React（默认）/ Vue 3；Android / iOS → Flutter（默认，单代码库覆盖双端）/ React Native / 原生；HarmonyOS → ArkTS + ArkUI；桌面三端（Windows / Linux / macOS）→ Tauri 2（默认，单代码库覆盖）/ Electron / Qt | 技术文档阶段（S3）按端确认方案并写入项目记忆；生成后强制编译校验 |
| 后端技术栈    | **技术文档阶段由用户确认**，推荐 NestJS 或 FastAPI 模板起步                              | 一旦确定即写入项目记忆并全程遵守                              |
| 打包分发     | Tauri Updater / electron-updater，均出 NSIS 安装包                          | 双形态共用同一版本号与更新通道                               |

### 架构概览

```
┌──────────────────────────────────────────────────────────────┐
│                EveryoneCoding 桌面客户端 (Windows)             │
├──────────┬──────────┬───────────┬────────────────────────────┤
│ 可视化设计器 │  记忆中心   │  AI 工作台  │  工程与 Git 面板             │
├──────────┴──────────┴───────────┴────────────────────────────┤
│              应用内核：状态管理 / 撤销重做 / 事件总线 / 命令系统        │
├──────────────────────────────────────────────────────────────┤
│ 本地服务层：SQLite(FTS5+vec) │ 文件工程读写 │ Git │ 进程管理 │ 预览服务  │
│                  ↑ 代码写入口唯一：仅 AI 生成层可写                  │
├──────────────────────────────────────────────────────────────┤
│ AI Provider 适配层：OpenAI / Anthropic 协议 │ 流式 │ 重试限流埋点   │
└───────────────┬──────────────────────────────┬───────────────┘
        ┌───────▼────────┐            ┌────────▼───────┐
        │  云端账号服务     │            │  第三方 AI 中转   │
        │  仅注册/登录      │            │ OpenAI/Anthropic│
        └────────────────┘            └────────────────┘
```

四条关键数据流：

1. **设计 → 记忆**：设计器 DSL → 结构精简器 → 分层写入页面 / 项目 / 功能记忆。
2. **记忆 → AI**：上下文引擎按 Token 预算与优先级组装「记忆 + 备注 + 需求 + 技术文档」→ 提交模型。
3. **AI → 代码**：生成代码 → 写入工程（唯一写入口）→ 记录代码锚点 → Git 自动提交（可配置）→ 预览热更新。
4. **交互 → 记忆**：用户纠正 / 反复 debug / 文档关联 → 自动写入或提示写入对应层级记忆。

## 四、快速开始

> ✅ **工程底座已初始化（Wave 0 完成）**：pnpm 单体仓库、双形态外壳、渲染层骨架、SQLite 存储层与 UI 组件库均可运行。
> 开发环境搭建详见 [docs/DEV-SETUP.md](docs/DEV-SETUP.md)。

### 环境要求

| 依赖                       | 版本要求               | 用途                       |
| ------------------------ | ------------------ | ------------------------ |
| Node.js                  | ≥ 22 LTS           | 前端构建与 Electron 主进程       |
| pnpm                     | ≥ 9                | monorepo 包管理（版本已锁定）   |
| Rust 工具链（stable）         | ≥ 1.77             | 构建 Tauri 2 外壳（仅 Tauri 版） |
| Microsoft Visual Studio  | C++ 生成工具 + Windows 10/11 SDK | Tauri 与原生模块编译   |
| WebView2 Runtime         | 常青版                | Tauri 版渲染（缺失时自动引导安装）     |
| Git                      | ≥ 2.40             | 仓库管理与 git2 回退通道         |

### 安装与运行

```bash
# 1. 克隆内部仓库（私有，需授权访问）
git clone <内部仓库地址>
cd everyoneCoding

# 2. 安装依赖
pnpm install

# 3. 质量门禁
pnpm lint && pnpm typecheck && pnpm test

# 4. 启动桌面客户端（开发模式）
pnpm dev:tauri      # Tauri 2 形态（需 Rust 工具链）
pnpm dev:electron   # Electron 形态
pnpm dev:renderer   # 仅渲染层（mock 外壳，浏览器可跑）

# 5. 构建安装包
pnpm build:tauri    # 产出 Tauri NSIS 安装包
pnpm build:electron # 产出 Electron NSIS 安装包
```

首次启动时需要在「模型接入」页面配置 Provider：支持任意兼容 OpenAI 或 Anthropic 协议的第三方中转，API Key 经 Windows DPAPI 加密后仅存本地。也可在「远程配置」页面填写自维护的配置源地址（产品不提供官方远程配置服务）。

## 七、关键设计决策

以下决策已由产品方确认，需求细节与实现必须与其保持一致。

| 编号   | 决策项     | 结论                                                    |
| ---- | ------- | ----------------------------------------------------- |
| D-01 | 客户端外壳   | Tauri 2 与 Electron **双形态并存**，用户自选下载，功能等价               |
| D-02 | 记忆同步    | **只做本地存储 + 手动导出 / 导入**（`.ecpkg`），不做云端自动同步             |
| D-03 | 多端产物   | **必须真实生成七端中所选目标端代码**（Web / Android / iOS / HarmonyOS / Windows / Linux / macOS）；各端方案在技术文档阶段由用户确认：默认 Web 用 React，移动双端用 Flutter（单代码库），HarmonyOS 用 ArkTS + ArkUI，桌面三端用 Tauri 2（单代码库） |
| D-04 | 技术栈与写入  | 技术选型在技术文档阶段询问用户后确定；**代码与数据库脚本一律不允许用户手动修改，只能由 AI 生成** |
| D-05 | 团队协作    | **v1.x 不支持**多人共享项目与记忆                                 |
| D-06 | 远程配置    | 不提供平台运营的远程配置服务，改为客户端内「远程配置页面」由用户自维护                   |
| D-07 | 重命名范围   | **仅项目内生效，不跨项目联动**                                     |
| D-08 | 数据库改名   | DDL 由 AI 生成迁移脚本，用户确认后可一键执行                            |
| D-09 | `.ecpkg` | **不对接对象存储、不生成云端分享链接**，仅本地文件                           |
| D-10 | 中文命名    | 组件名与标识符用英文 / 拼音，显示文案保留中文                              |

### 贯穿全项目的硬约束

1. **AI 是代码与数据库脚本的唯一写入口** — 客户端代码视图为只读，用户不可手动编辑，一切修改通过 AI 生成完成。
2. **数据本地优先** — 项目、记忆、文档全部存放本地；云端仅承担账号注册 / 登录与版本更新。
3. **不跨项目自动联动** — 跨项目复用通过 `.ecpkg` 文件手动导入完成。
