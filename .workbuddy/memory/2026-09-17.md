## 排查：「设置尚未连接本地配置」提示的根因（主人提问）

**结论：不是故障、不是配置缺失，是端口未装配（功能未接线），属 `docs/ACCEPTANCE-REPORT.md` 已记录的 Wave 9 遗留项（L-04 / §3 第 109 行、`docs/E2E-CHECKLIST.md M-07`）。**

- 渲染层走「端口注入」架构：领域能力由外壳装配后挂 `globalThis.__EC_*__`。
- `__EC_SETTINGS__` **全仓只有读取方，零写入方**：`settings-api.tsx:123` `readInjectedSettingsApi()`、
  `pages/SettingsPage.tsx:29`，其余命中全是错误文案与 docs。→ 恒为 `null`。

  的 `createRendererAiSettings(shell.ai)`），因为 `ShellCapabilities` 里有 `ai: boolean`。
- 而 `packages/shell-api/src/types.ts` 的 `ShellCapabilities`（313-326 行）**没有 `settings` 字段**，
  `ShellHost`（329-343 行）也没有 settings 成员 → 契约层就没定义生产者，不是漏调用。
- `apps/renderer/src/runtime/` 下只有 `ai-settings.ts`；`features/settings/` 下只有
  `update-service-host.ts`，**无 `settings-service-host.ts`**。
- 数据层其实已就绪：`packages/core/src/settings.ts` 的 `settingsStore`（zod 校验 + 订阅 + 迁移）

**为什么「每个类目都提示」**：`SettingsHome.tsx:99` 的 `{!api ? <SettingsUnavailable /> : null}`
**无条件渲染、不随类目切换**；同时 5 个面板都被 `api &&` 挡住（100-104 行），
所以只剩提示语。另外默认类目在 `api` 为 null 时跳到 `'ai'`（`SettingsBody` 第 80 行
`useState(api ? 'general' : 'ai')`），因此第一眼看到「提示 + 模型服务」。
`BudgetSettings` 对 null 有防护（53 行 `if (!api)`），不会崩。

**同类未装配端口**：`__EC_USAGE__`（用量类目）、`__EC_UPDATE__`（更新类目，`SettingsPage`
甚至没传 `updateApi`）同样无生产者；`__EC_WORKSPACE__`/`__EC_DOCS__`/`__EC_AUTH__` 亦同（M-07 四端口）。

### 关键设计决定（后续务必遵守）

1. **不注入未装配的域**。`describe()` 报 false 时保持不注入，页面保留现有装配引导。
   注入半成品端口会让用户看到"能打开但每个动作都失败"的界面，**比现状更差**。
2. 错误跨进程只传 `{code,message}` 并脱敏；渲染层还原为 `ShellError` 按 code 分支。
3. `DocsApi.supportedFormats()` 是同步签名，装配时取一次闭包缓存（取不到退化为 `[]`）。

## 修复：`git push -u origin main` 报 `failed to push some refs`（主人指派）

**结论：不是单一故障，是三层独立原因叠加，且报错文案相同，必须逐层排除，不可按"网络/权限"一把梭。**

| 层 | 根因 | 证据 |
| --- | --- | --- |
| L1 触发 | 本地 `main` 分支**零提交**，不存在可推送的 `main` ref | `git status` → `## No commits yet on main`，全部文件 `??`；`git log` → `does not have any commits yet` |
| L2 阻断 | `~/.ssh` 下**只有 known_hosts，无任何私钥** | `ssh -T git@github.com` → `Permission denied (publickey)`；`ssh -v` 显示 8 类 identity 全 `type -1` |
| L3 隐患 | `apps/desktop-electron/release/`（274.9 MB，含 **180 MB** `EveryoneCoding.exe`）未被 .gitignore 覆盖 | `.gitignore` 只有 `dist/ build/ out/`，**没有 `release/`**——而它正是 electron-builder 默认输出目录 |

L3 与报错文案的关系：GitHub 单文件硬限 100 MB，超限同样以 `failed to push some refs` 收尾。
即 L1 修好后 L3 会立刻接手继续失败，**必须与 L1 同时修**，否则会误判"改了没生效"。
