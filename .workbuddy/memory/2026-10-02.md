## CI 修复收口（续 2，同会话）：第五个失败——harness 看门狗误伤验签

main push CI（36970460347，提交 41e88dc）Test 又挂：`electron-updater-host.test.ts` **签名错误用例**期望 `UPDATE_SIGNATURE` 实得 `UPDATE_NETWORK: 下载停滞 2s`。根因：Authenticode 验签期间**没有任何下载进度事件**，CI 机器慢时验签超过 harness **硬编码的 `stallTimeoutMs: 1500`**，看门狗把验签阶段误判成网络停滞。同一提交在分支 CI（36969783534）刚全绿、到 main 就挂——机器速度方差实锤偶发（此前 designer/code-page 的教训同款：分支绿 ≠ main 绿，方差型 flaky 要多轮压力）。

修复（提交 **2d54620**，分支 `ci-fix-flaky2`，CI run 36971422248 验证后合 main）：harness 不再全局硬编码 `stallTimeoutMs: 1500` + `createCancellationToken`，缺省与生产一致（不启用看门狗）；只有停滞看门狗专测显式传 `stallTimeoutMs: 1500`。本地 updater 套件 8 轮 × 12 全绿。

**方法论沉淀（flaky 收口三连）**：CI 偶发失败的处置顺序——① 同 run 两遍执行一红一绿即实锤；② 断言/超时值对慢环境的容忍度逐个审（fireEvent act() 窗、findBy 默认 1s、测试 harness 的激进超时全局共享）；③ 修复后多轮压力（单文件 50 轮 / 全套件 4 轮 / 套件 8 轮）再推。**分支验证 → main 复挂**说明 7 分钟的单次 CI 运行本身方差就大，重要修复合 main 后要盯 push 触发的那次运行。
