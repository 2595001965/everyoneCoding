## 排查：「设置尚未连接本地配置」提示的根因（主人提问）

**结论：不是故障、不是配置缺失，是端口未装配（功能未接线），属 `docs/ACCEPTANCE-REPORT.md` 已记录的 Wave 9 遗留项（L-04 / §3 第 109 行、`docs/E2E-CHECKLIST.md M-07`）。**

关键证据链（全仓 `!dist` 检索）：

- 渲染层走「端口注入」架构：领域能力由外壳装配后挂 `globalThis.__EC_*__`。
- `__EC_SETTINGS__` **全仓只有读取方，零写入方**：`settings-api.tsx:123` `readInjectedSettingsApi()`、
  `pages/SettingsPage.tsx:29`，其余命中全是错误文案与 docs。→ 恒为 `null`。
- 对照：`__EC_AI_SETTINGS__` 有真实装配（`main.tsx:36-44` 经 `runtime/ai-settings.ts`
  的 `createRendererAiSettings(shell.ai)`），因为 `ShellCapabilities` 里有 `ai: boolean`。
- 而 `packages/shell-api/src/types.ts` 的 `ShellCapabilities`（313-326 行）**没有 `settings` 字段**，
  `ShellHost`（329-343 行）也没有 settings 成员 → 契约层就没定义生产者，不是漏调用。
- `apps/renderer/src/runtime/` 下只有 `ai-settings.ts`；`features/settings/` 下只有
  `update-service-host.ts`，**无 `settings-service-host.ts`**。
- 数据层其实已就绪：`packages/core/src/settings.ts` 的 `settingsStore`（zod 校验 + 订阅 + 迁移）
  已存在，但**仅内存态**（`toJSON`/`fromJSON` 需外部持久化），`main.tsx:52` 只读到 `theme`。

**为什么「每个类目都提示」**：`SettingsHome.tsx:99` 的 `{!api ? <SettingsUnavailable /> : null}`
**无条件渲染、不随类目切换**；同时 5 个面板都被 `api &&` 挡住（100-104 行），
所以只剩提示语。另外默认类目在 `api` 为 null 时跳到 `'ai'`（`SettingsBody` 第 80 行
`useState(api ? 'general' : 'ai')`），因此第一眼看到「提示 + 模型服务」。
`BudgetSettings` 对 null 有防护（53 行 `if (!api)`），不会崩。

**同类未装配端口**：`__EC_USAGE__`（用量类目）、`__EC_UPDATE__`（更新类目，`SettingsPage`
甚至没传 `updateApi`）同样无生产者；`__EC_WORKSPACE__`/`__EC_DOCS__`/`__EC_AUTH__` 亦同（M-07 四端口）。

**修复路径（未实施，待主人决定）**：补 `runtime/settings-service-host.ts` 适配器 →
`ShellCapabilities` 加 `settings` + `ShellHost` 加成员 → Electron/Tauri 主进程实现
（fs 持久化 settings JSON + SQLite 读写 + 数据目录迁移）→ `main.tsx` 按能力协商注入。
工作量：契约层半小时，主进程实现按方法分档（`exportProject`/`migrateDataDirs` 最重）。

## 四端口装配：已落地共享装配层（主人要求「把这四个端口接一遍」）

### 做了什么（全部已过门禁）

新增 **`@ec/shell-api` 的域端口 RPC 契约**，四个端口此后共用一个通道 + 方法白名单分发，
不再各开一套 IPC（四域合计 70 个方法，逐方法开通道会让 preload 白名单无法审阅）：

- `packages/shell-api/src/domain-control.ts`（新）：`DOMAIN_KINDS` 四域、
  `DOMAIN_RPC_METHODS`（workspace 19 / docs 20 / auth 14 / settings 16，与四个端口接口逐字对应）、
  `DomainRpcRequest/Response`、`DomainDescriptor`、`DomainControlHost.describe()`、
  `sanitizeDomainMessage`（脱敏）、`createLocalEmitter`（订阅型能力本地分发）。
- `types.ts`：`ShellCapabilities.domain: boolean` + `ShellHost.domain`。
- `index.ts`：导出域契约；`negotiate()` 降级兜底补 `domain: false`。
- `mock.ts`：`createMockDomainControlHost()`（四域如实报不可用）+ `domain` 能力位 + `options.domain`。
- `contract.ts`：能力清单补 `domain`（顺带把失真的测试名「十类能力」改为「完整的能力结构」——
  清单其实早已 11 项）。
- Electron：`ec:domain:invoke` / `ec:domain:describe` 通道、`main/ipc/domain.ts`
  （`registerDomainIpc` + `registerUnavailableDomainIpc` 兜底）、`IpcDependencies.domainHost`、
  preload `domain.invoke/describe`（进 `PRELOAD_TOP_LEVEL_KEYS` 与安全面自检）、
  bridge 挂 `domain` 并把 `capabilities().domain` 设为 true。
- Tauri：`domain` 成员如实返回 NOT_SUPPORTED，`capabilities().domain = false`
  （与既有 `ai: false` 同一口径）。
- 渲染层 `apps/renderer/src/runtime/domain-ports.ts`（新）：把 `shell.domain` 映射为四个端口
  （`createWorkspaceApi`/`createDocsApi`/`createAuthApi`/`createSettingsApi`）+
  `installDomainPorts()` 按 `describe()` **只注入 available 的域**；`main.tsx` 接入并在启动日志
  打印「已装配域」与「未装配域及原因」。
- 测试：`domain-control.test.ts`(12) + `domain-ipc.test.ts`(9) + `domain-ports.test.ts`(13) 全绿。

### 关键设计决定（后续务必遵守）

1. **不注入未装配的域**。`describe()` 报 false 时保持不注入，页面保留现有装配引导。
   注入半成品端口会让用户看到"能打开但每个动作都失败"的界面，**比现状更差**。
2. 错误跨进程只传 `{code,message}` 并脱敏；渲染层还原为 `ShellError` 按 code 分支。
3. `DocsApi.supportedFormats()` 是同步签名，装配时取一次闭包缓存（取不到退化为 `[]`）。
